# 技术可行性与方案选型

> 本文回答三个问题：能不能做到、哪条路最稳、哪些说法是错的。
>
> 结论基于 2026-10-22 的公开资料调研；P0 已在 2026-10-22/23 用本机实测更新（见 `spike/REPORT.md`）。
> 本机环境：Windows 11 26200（家庭版中文版）、单显示器 2560×1600 @150%、Intel 核显 + RTX 5060 Laptop、.NET 8 SDK、Edge 已安装。

> **⚠️ P0 实测更新（重要）**
> 完全离屏的窗口，WGC **只保留最后一帧**，不会持续产生新帧；从未可见的窗口客户区是空白。`PrintWindow + PW_RENDERFULLCONTENT` 在离屏状态下是**实时**的（FixtureApp 连续 8 次拉取 8 个不同 hash，p50≈12ms）。
> 因此主路径已改为：**离屏原生窗口 → PrintWindow；WGC 仅用于可见窗口 / VDD；网页 → 无头 Edge + CDP**。详见 `spike/REPORT.md`。

## 1. 结论先行

1. **没有"让任意应用直接渲染到内存"的通用 API。** 能做到的是：让窗口在 Windows 眼里是正常显示状态（DWM 持续合成），但它位于物理显示器之外。这已经是"不占屏幕"的可行定义。
2. **离屏主路径 = PrintWindow + `PW_RENDERFULLCONTENT`。** 它会触发窗口绘制/取重定向表面，因此在窗口完全离屏时仍能拿到当前画面；P0 实测 8/8 帧变化，p50≈12ms。它对 GPU 合成应用（Chromium/部分 Electron/WinUI）的兼容性仍需实测。
3. **WGC 的定位改为"可见 / 虚拟显示器（VDD）的连续帧后端"。** 完全离屏时 WGC 冻结在最后一次可见绘制；1px 露出也不能保活。P0 实测：可见窗口 10/10 帧变化，离屏 1/20。
4. **网页目标不要走"GUI 浏览器"路线，直接无头 Edge + CDP。** 这是唯一真正"零窗口、零合成、零打扰"的路径，而且能拿到 DOM、console、网络失败，最适合前端视觉验证。
5. **输入没有官方"按窗口注入"的 API。** 常见说法"`InjectSyntheticPointerInput` 可以指定 hwndTarget"是**错的**：它只接受触摸/笔，坐标是全屏坐标，没有 hwnd 参数。输入必须分层：UIA → CDP → 窗口消息 → 最后才是有侵入性的 SendInput。
6. **虚拟显示器（IddCx VDD）是"系统认为在显示、但人看不到"的通用方案**，也是 WGC 连续帧/PrintWindow 失败应用的保真兜底。但需要管理员安装驱动，v1 不捆绑、不自研，只做"检测 + 适配"。
7. **RDP / 隐藏桌面 / Windows 服务 三条路都不通**：RDP 会踢掉控制台会话（家庭版根本没有 RDP 服务端）；隐藏桌面 DWM 不合成；服务在 Session 0，看不到用户窗口。
8. **"停泊"省掉的是视觉与注意力成本，不是 GPU 成本。** 像素仍然要被渲染、被合成；我们消除的是闪窗、抢焦点、共用光标和隐私泄露，不是渲染开销。这一点必须对用户讲清楚。

## 2. Windows 图形栈的最小背景

- 应用窗口的内容由应用自己渲染（GDI / D3D / DirectComposition / Web 渲染管线），DWM 负责最终合成到显示器。
- **Redirection surface**：DWM 为每个窗口维护一份合成表面。只要窗口处于"显示"状态（未最小化、未隐藏、未被 cloaked），DWM 就会持续更新它——即使窗口被别人完全遮住。
- **WGC（Windows.Graphics.Capture）** 正是从这个合成层取图，所以"被遮挡"不影响；"最小化/隐藏/在另一个虚拟桌面"则会让它拿不到内容（cloaked / surface 被丢弃）。
- **PrintWindow** 是另一条路：它给窗口发绘制请求（`WM_PRINT` 或取重定向表面），把结果画到调用方提供的 DC 上。它不依赖窗口是否在屏幕上，但依赖应用/渲染器是否配合。
- **DXGI Desktop Duplication** 复制的是"某个显示器的输出"，不是单个窗口；它适合配合虚拟显示器使用。
- **输入**：Windows 的输入队列是会话级/桌面级的。没有"只发给某个后台窗口"的通用输入通道；UIA 是跨进程语义调用（不是输入注入），窗口消息是应用自己处理的消息，二者都不需要前台焦点，但覆盖面有限。

## 3. 捕获路线对比

| 方案 | 原理 | 窗口需要"可见"吗 | 能拿 GPU 合成内容 | 连续帧 | 额外依赖 | 结论 |
|---|---|---|---|---|---|---|
| **WGC 按窗口** | 从 DWM 的窗口合成表面取帧 | 需要 shown + restored + 未 cloaked；**离屏会冻结在最后一帧** | 是 | 是（仅可见时） | 无（Win10 1803+） | **仅可见/VDD** |
| **WGC 显示器 + 虚拟显示器** | 窗口放到 VDD 上，按显示器捕获 | 在虚拟显示器上正常显示 | 是 | 是 | IddCx 驱动 + 管理员安装 | **保真兜底（可选）** |
| **DXGI Desktop Duplication** | 复制显示器输出 | 必须落在某个真实/虚拟输出上 | 是 | 是 | 同上 | 仅配合 VDD |
| **PrintWindow + `PW_RENDERFULLCONTENT`** | 让窗口把内容画到指定 DC / 取重定向表面 | 不需要可见；离屏可实时 | 大多可以，但应用相关 | 是（拉取式） | 无 | **离屏主路径** |
| **BitBlt / GetWindowDC** | GDI 屏幕/窗口 DC 拷贝 | 需要可见，且被遮挡会缺内容 | 否 | 否 | 无 | 遗留应用兜底 |
| **无头 Edge + CDP** | 浏览器内部渲染，不创建窗口 | 不需要窗口 | 是（Web 内容） | 是（按需） | Edge / Chrome | **网页首选** |
| **隐藏桌面（CreateDesktop）** | 在非当前桌面启动应用 | DWM 不合成非当前桌面 | 否 | 否 | 无 | **排除** |
| **DWM 缩略图** | 把窗口缩略图合成到宿主窗口 | 源窗口需可合成 | 是 | 是 | 宿主窗口 | **排除**（宿主仍需被捕获，且最小化失效） |
| **RDP 回环 / 第二会话** | 独立会话渲染 | 是 | 是 | 是 | RDP + 许可 | **排除**（会踢掉/锁定人类会话） |

### 3.1 关键细节与风险

**WGC**
- 按窗口捕获用 `IGraphicsCaptureItemInterop.CreateForWindow(hwnd)` 创建 item，再用 `Direct3D11CaptureFramePool` 拉帧。遮挡不影响。
- **P0 实测**：窗口完全离屏后，20 次捕获只有 1 个唯一 hash；画面停在最后一次可见绘制。1px 露出也不行。可见窗口 10/10 帧变化。不要把它当离屏实时后端。
- 最小化、`SW_HIDE`、切到其他虚拟桌面（窗口被 cloak）都会导致黑帧/停帧。**必须在每次捕获前检查窗口状态**，并持续 watch。
- 捕获边框：Win11 的 `IsBorderRequired=false` 需要 **MSIX 打包 + `graphicsCaptureWithoutBorder` 能力 + 用户授权**，未打包程序无法关闭。幸运的是窗口在屏幕外，边框也画在屏幕外，人看不到。v1 接受这个限制（ADR-007）。
- 混合显卡（本机 Intel + NVIDIA）下，帧纹理所在适配器与捕获设备不一致可能导致拷贝失败，需要实测并允许指定适配器。
- 离屏窗口是否持续产出新帧：**LIKELY**，M0 必测。若失败，Plan B 见 §6。

**PrintWindow**
- `PW_RENDERFULLCONTENT = 2` 是未公开但被广泛使用的标志，Chromium 自己的截图代码也用过。
- 对经典 Win32/WPF 通常可用；对 Chromium/Electron/WinUI3 时好时坏，Win11 上有整窗纯色/全黑的报告。
- 这是"拉取式"的：每次调用都可能触发应用重绘，不适合高频；适合作为 WGC 失败时的一次性兜底。
- 需要检测两种情况：全黑/纯色（空白检测）、与上一帧完全相同（过期检测）。

**虚拟显示器（VDD）**
- IddCx 虚拟显示器会像真实显示器一样出现在"设置 > 显示"里（这是可见的 UI 痕迹，但不在工作区里弹窗）。
- 窗口用 `SetWindowPos` 移到虚拟显示器坐标即可，DWM 会正常合成；再用 WGC 显示器捕获或 DXGI 复制取图。
- 可用的签名驱动：Parsec VDD（签名，但**许可证不允许随产品再分发**）、MTT/VirtualDrivers 的 Virtual-Display-Driver（开源、发布版做了 attestation 签名，需核对 LICENSE）、微软 IddSampleDriver（仅示例，不可分发）。
- 需要管理员安装，部分环境需要重启。v1 只做检测与适配，不捆绑（ADR-008）。

**无头 Edge + CDP**
- 本机已安装 Edge（`C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`），支持 `--headless=new` 与 CDP。
- 无窗口、无 DWM 合成、无任务栏/Dock 痕迹；可精确设置视口、DPR、UA；可拿 DOM、console、network、JS 执行。
- 这是"前端视觉验证"场景的最优解，也是整个项目最容易做到 0 打扰的部分。

**被排除的方案**
- **隐藏桌面**：应用可以在上面运行，但 DWM 不合成非当前桌面，WGC 拿不到帧；PrintWindow 对 GPU 内容不可靠。无法满足"真实图像"。
- **Windows 服务**：Session 0 隔离，看不到用户窗口。daemon 必须是交互式会话里的托盘程序。
- **RDP 回环**：Windows 7 起就按设计阻止 localhost 回环；用机器名回环会让同一用户的控制台会话被断开（人被迫锁屏）；多会话需要非法的 termsrv 补丁；家庭版没有 RDP 服务端。
- **`SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`**：这是"防止被捕获"，不是"隐藏窗口"；被设置的目标我们要检测并报错，而不是试图绕过。

## 4. 输入路线对比

| 策略 | 跨进程 | 需要前台焦点 | 移动真实光标 | 可靠性 | 适用 | 备注 |
|---|---|---|---|---|---|---|
| **UIA 模式**（Invoke/Value/Toggle/Selection/ExpandCollapse/Scroll） | 是 | 否 | 否 | 高，但取决于 provider | 原生控件、按钮、输入框、菜单 | 不是输入注入，是语义调用；个别实现会自行激活窗口 |
| **CDP**（`Input.dispatchMouseEvent` / `insertText` / `dispatchKeyEvent`） | 是 | 否 | 否 | 高 | 网页、我们启动的 Chromium/Electron | 需要目标暴露调试端口（我们启动时加） |
| **窗口消息**（PostMessage/SendMessageTimeout + WM_*） | 是 | 否 | 否 | 中 | 经典 Win32、WPF、部分 Qt | Chromium 会忽略发给 HWND 的鼠标消息；键盘要处理 lParam/扫描码/IME |
| **SendInput + 临时焦点** | 是 | 是 | 鼠标会 | 高但侵入 | 最后手段 | 会抢焦点、移动光标、可能把按键漏给人的窗口；默认禁用，需显式授权 |
| **InjectSyntheticPointerInput** | — | — | — | **不适用** | 仅触摸/笔 | 没有 hwnd 参数，坐标是全屏坐标；无法打到离屏窗口 |

### 4.1 一个必须纠正的流行误解

网上不少文章/代码声称可以用 `CreateSyntheticPointerDevice(PT_MOUSE, ...)` + `POINTER_TYPE_INFO.mouseInfo.hwndTarget` 向后台窗口注入鼠标。**这不符合官方 API**：

- `CreateSyntheticPointerDevice` 的 `pointerType` 只接受 `PT_TOUCH` / `PT_PEN`（鼠标类型被拒绝）；
- `POINTER_TYPE_INFO` 只有 `touchInfo` / `penInfo`，没有 `mouseInfo`；
- 注入坐标是**虚拟屏幕坐标**，会落到该坐标处的窗口，无法指向离屏窗口。

所以它不能作为本项目的输入基础。不要在这条路上浪费时间。

### 4.2 键盘的现实

- 没有任何官方 API 可以"只给某个后台窗口发键盘"。`SendInput` 是会话级的，`PostMessage(WM_KEYDOWN/WM_CHAR)` 是应用自己处理的消息。
- 因此：
  - 网页/Electron：用 CDP 的 `Input.insertText` / `dispatchKeyEvent`，这是最可靠的。
  - 原生输入框：优先 UIA `ValuePattern.SetValue`；其次 `WM_CHAR` 逐字发送（Unicode，绕过 IME/死键问题）。
  - 快捷键：优先 UIA 找到对应菜单/按钮直接调用；其次 `WM_COMMAND`；再次 `PostMessage` 组合键；最后才是焦点切换 + `SendInput`。
- 中文输入：不要模拟 IME 组合，直接发送 Unicode 字符（`WM_CHAR` / CDP `insertText` / UIA SetValue）。

## 6. 主路径失败时的 Plan B

P0 后更新：

1. **WGC 离屏冻结（已确认）** → 不再使用 WGC 作为离屏主路径；改用 PrintWindow。
2. **1px 露出（已测）** → 仍冻结，放弃该方案。
3. **PrintWindow 对某应用失败/全黑** → 优先用 VDD（用户自装虚拟显示器）；Chromium/Electron 用受控 CDP 启动；最后才考虑“短暂可见 + WGC”并显式告知用户。
4. 对**必须真实输入**的应用，提供"独占输入模式"：真实 `SendInput`，但把光标临时移到看不见的虚拟屏坐标；必须显式授权，且检测到人类正在输入时拒绝执行。

## 7. 已知限制（必须在产品中如实呈现）

1. **完全离屏窗口的 WGC 会冻结在最后一帧**；离屏实时依赖 PrintWindow。WGC 只适合可见窗口/VDD。
2. **PrintWindow 对 Chromium/Electron/UWP/WinUI 的兼容性并不一致**：P1-11 实测 Edge GUI（Chromium）完整、Calculator（UWP）完整、VS Code（Electron）只有窗口 chrome。Electron 需 CDP；其他应用逐项入矩阵。PrintWindow 也可能阻塞，需要超时与降级。
3. 最小化、隐藏、切到其他虚拟桌面、被 cloak 的窗口无法捕获（黑帧/停帧）。
2. 设置了 `WDA_EXCLUDEFROMCAPTURE` 的窗口（受保护内容）无法捕获。
3. 独占全屏、DRM、硬件覆盖层（部分视频播放器）不在支持范围。
4. 提权窗口需要 daemon 也提权，否则 UIA/消息/截图都会被 UIPI 拦。
5. 单实例应用（Excel、部分聊天工具）可能无法独立启动第二个实例；只能接管已有窗口（需要用户同意，且会移动人的窗口）。
6. 停泊仍然消耗 GPU/合成资源；不是"零成本"。
7. 某些应用会自我纠正窗口位置、依赖显示器尺寸、或在离屏时停止动画；需要 watch + 降级。
8. 输入隔离是分层的：UIA/CDP 路径可以做到不抢焦点；消息路径覆盖有限；SendInput 路径一定有侵入性。
9. 截图是"某一时刻"的画面；动画/视频需要显式等待稳定，无法保证与人的感知完全同步。
10. 家庭版没有 RDP 服务端；企业多会话方案不在支持范围。
