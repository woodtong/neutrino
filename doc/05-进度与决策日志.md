## 2026-10-22 / 立项与方案

**做了**
- 明确问题：Agent 共享物理屏幕导致的闪窗、抢焦点、抢光标、无法并行、隐私噪声。
- 完成两轮技术调研：窗口捕获（WGC/PrintWindow/VDD/隐藏桌面/RDP）与后台输入（UIA/CDP/消息/SendInput/合成指针）。
- 确定主路径：离屏停泊 + WGC 按窗口捕获；网页走无头 Edge + CDP；输入分层；VDD 作为可选兜底。
- 写出 `00`–`04` 五份文档：概览、可行性、架构、接口、路线图。

**关键结论/决策**
- **纠正**：`InjectSyntheticPointerInput` 不支持鼠标、也没有 `hwndTarget`，不能用于按窗口注入。不要在这个方向投入。
- **纠正**：Windows 服务（Session 0）无法捕获/操作用户窗口；daemon 必须是交互式会话里的托盘程序。
- **排除**：RDP 回环（会踢掉控制台会话，家庭版无服务端）、隐藏桌面（DWM 不合成）、DWM 缩略图（无法离屏取回）。
- **待验证**：离屏窗口的 WGC 是否持续出新帧（H1）——这是主路径成立与否的关键，M0 第一项。
- **取舍**：v1 不打包 MSIX，接受离屏窗口的黄色捕获边框（边框在屏幕外，人看不到）。
- **取舍**：不捆绑/不自研 VDD 驱动，只做检测与适配；驱动签名与许可是不可控成本。

**证据**
- 调研来源见 `01-技术可行性与方案选型.md` §8。
- 本机环境检查：dotnet 8.0.418、Edge 存在、Windows SDK 26100、单显示器。

## 2026-10-22 / 市场与需求调研

**做了**
- 四条线并行调研：Agent 云桌面/沙箱、无头浏览器基础设施、Windows 桌面自动化、平台原生能力与需求规模。
- 核实关键事实：微软 Agent Workspace（2025-10-16，实验性，独立账户+独立桌面，第三方 API 私测）、Windows 365 for Agents（云端 Cloud PC）、阿里云 AgentBay（云端 Windows/Linux + MCP）、UiPath PiP（同机独立会话但显示预览窗、一次一个）、Browserbase 定价、GitHub stars（2026-10-22）。
- 产出 `06-市场与需求调研.md`：竞品矩阵、六个最接近替代品、需求评分、TAM/SAM/SOM、收益模型、威胁与定位。

**关键结论**
- **网页层没有机会**：Playwright MCP 38.5k stars、Chrome DevTools MCP 54k stars、云端浏览器 $0.02–0.12/小时；"前端截图不弹窗"已被免费解决。
- **空位在本地原生 Windows**：本地 + 原生应用 + 对人不可见 + MCP + 多 Agent，截至 2026-10 未发现成熟产品。
- **最大威胁是微软 Agent Workspace**：和我们的核心价值高度重叠，但仍是实验性、生态封闭、第三方 API 私测；时间窗约 12–24 个月。
- **最稳的付费楔子是 CI 无头/并行 Windows UI 测试**：WinAppDriver 已死、Appium 单会话、RDP/tscon 土办法；客单价比个人订阅高。
- **商业上是小而美**：TAM 约 $0.22–0.49B，SAM 约 $8–20M，SOM 三年 $0.3–5M；基准三年约 $1.4M ARR，不是风投级。

**决策**
- **继续做，但换定位**：从"隐形屏幕"改为"Windows 上给 Computer-Use Agent 的本地执行层"；网页是内置能力，不是卖点。
- MVP 收窄：原生停泊/捕获 + UIA/输入 + MCP + 多 target + 无头 Edge；面板、VDD、安装器后置。
- 先开源/个人开发者验证留存，再做 Team/CI；不自研驱动。
- 设定 kill/pivot 条件（见 `06` §9.4），尤其是"微软开放 Agent Workspace API"和"10 个设计伙伴中 <3 个周活"。

**下一步**
1. M0 可行性尖刀（离屏 WGC 等 9 条假设）+ 10–15 个用户访谈并行。
2. 做一个 90 秒 demo（人打字 + Agent 在看不见的窗口里截图/点击）。
3. 用 demo 换 20 个设计伙伴，再决定是否进入 M1。

**遗留/风险**
- 部分市场规模为分析机构估算，口径差异大；TAM/SAM/SOM 是自建假设，不可对外当预测。
- 微软 Agent Workspace 的 GA 时间未官方确认；需持续跟踪。
- 社区痛点证据部分来自二手摘要，具体 issue 链接未逐一打开。

**实测结果**
- **H1 不成立**：完全离屏窗口的 WGC 20 帧只有 1 个唯一 hash；从未可见时客户区空白；先可见后停泊会保留最后一帧但冻结；1px 露出仍冻结。可见窗口 WGC 10/10 帧变化。
- **PrintWindow 离屏实时**：FixtureApp 8/8 唯一 hash，帧号 39→49；p50≈11.9ms / p95≈13.0ms；Notepad 1920×1125 完整，WM_SETTEXT 后正文为 `hello 世界 123`。

- **焦点/剪贴板**：FixtureApp 全流程与 Notepad 操作前后前台不变、剪贴板 seq 不变；UIA 的异步激活由 `ForegroundGuard` 恢复。Notepad 初次无 NOACTIVATE 时会抢前台，已修复。
- **光标**：测试期间 `GetLastInputInfo` 变化 → 人类在操作；代码未调用 `SetCursorPos`，但需安静环境重测。
- **UIA/消息**：FixtureApp 17 元素；UIA Invoke/SetValue 成功；WinForms 类名需按 `BUTTON`/`EDIT` 包含匹配；BM_CLICK/WM_SETTEXT 成功。

**决策**
- 捕获顺序改为：web → CDP；离屏原生 → **PrintWindow**；可见/VDD → WGC；PrintWindow 失败再降级/报错。
- 停泊默认加 `WS_EX_NOACTIVATE`；短操作后用 `ForegroundGuard` 恢复被我们抢走的前台。
- `spike/REPORT.md` 为 P0 主报告；`spike/evidence/` 存证据。
- 测试暂用零依赖 runner（NuGet 初次 restore 不稳定）；P1 迁移 xUnit。

**做了**

- **VS Code**：PrintWindow ❌（只有三个窗口按钮，客户区纯深灰）；CDP ✅（`document.title=Visual Studio Code`，完整 workbench），`SW_SHOWMINNOACTIVE` 启动后前台不变。
- **Calculator**：PrintWindow ✅ 502×810 完整，UIA 50；**焦点不稳定**：多次抢前台，`SetForegroundWindow`/`AttachThreadInput`/`SwitchToThisWindow` 失败或偶发成功。
- 清理：三款窗口全部关闭，Edge GUI profile 进程 0，VS Code profile 删除。
- 新增 `PrintWindowCapture.TryCaptureWithTimeout`（6s），modern 探针已改用；超时返回结构化错误，但阻塞 worker 的隔离仍待做。

**决策**
- 原生 Chromium（Edge GUI）：PrintWindow 可作为捕获后端；输入/观测优先 CDP。

- UWP（Calculator）：捕获/UIA 可用，但默认不承诺"不抢焦点"；需要显式授权或独立会话，写入兼容矩阵。
- 启动策略：优先 `SW_SHOWMINNOACTIVE`/`--window-position` 避免激活；`WS_EX_NOACTIVATE` + 前台恢复作为兜底，但焦点隔离是概率性的。

## 2026-10-24 / 焦点安全与“执行优先”策略（0.4.1-dev）

**背景**
- 用户反馈：跑测试时能看到窗口闪烁，而且打字被打断。实测确认这是两个问题：测试夹具先在屏幕内创建再停泊；产品 UIA 动作会把前台切到屏幕外的停泊窗口。
- 用户进一步明确产品面向智能体：调用应尽量一次成功，拒绝只能是穷尽策略后的最后兜底，不能因为“用户正在打字”就让 Agent 收到失败。

**做了**
- 实测 `WS_EX_NOACTIVATE` 挡不住程序激活：WinForms 的 `InvokePattern.Invoke`/`ValuePattern.SetValue`，以及 WPF 的 `Invoke`/`SetValue`/`Toggle`/`Select`，都会把前台切到停泊窗口。窗口消息 `BM_CLICK`/`WM_SETTEXT`/`WM_KEYDOWN` 不改变前台，但把 `WM_LBUTTONDOWN`/`WM_CHAR` 发给未激活的 WPF 顶层 HWND 不会触发按钮或输入。
- 原生 `click_element`/`set_text` 改为**消息优先**：按 UIA bounds 找 HWND 子控件，按钮发 `BM_CLICK`，其他可交互控件发鼠标消息，EDIT/RICHEDIT 发 `WM_SETTEXT`。
- 无 HWND 时**自动走 UIA**：`click_element` 按 Invoke → Toggle → SelectionItem → ExpandCollapse 选择可用 pattern；`set_text` 用 ValuePattern；坐标 `click` 用 UIA `AtPoint` 找最小可执行元素；执行后由 `FocusGuard` 恢复前台。不再要求 `allow_focus_steal`，不再因用户活跃返回 `USER_ACTIVE`。
- `strict_no_focus_steal=true` 是可选严格模式：需要 UIA 时返回 `FOCUS_STEAL_NOT_ALLOWED`；默认 false。
- 只有控件没有任何可执行 pattern 时才返回 `ELEMENT_NOT_ACTIONABLE`；目标挂起/受保护/不可见沿用原错误码。
- `FocusGuard`：最多等 500ms 观察激活；若前台仍是 target，用 `SetForegroundWindow`/`AttachThreadInput` 恢复，并做 100ms 稳定校验；不用 `SwitchToThisWindow`；人类已切到第三个窗口时不抢回；恢复失败返回 `focus:"stolen"` + `FOCUS_STOLEN`，但动作已执行。
- 删除消息路径上的旧 guard（每次最多 160ms，且可能无谓切前台）。
- 测试夹具默认用 `GetParkPosition` 创建在屏外；WGC 可见窗口测试用 `GHOSTSCREEN_VISIBLE_TESTS=1` opt-in；新增 WPF UIA 回退测试，用 `GHOSTSCREEN_UIA_TESTS=1` opt-in（它会短暂激活夹具）；每个测试结束断言测试进程没有留下与虚拟屏相交的窗口。
- MCP 原生回合增加前台/光标/剪贴板不变量断言；检测到人类输入时跳过，避免共享桌面误报。

**证据**
- 临时焦点诊断（未进仓库）：夹具创建不抢前台；WinForms/WPF 的 UIA 动作会激活；WPF 消息点击不触发、`WM_CHAR` 不生效；`FocusGuard` 在 WPF 上返回 `Restored`，前台回到原窗口。
- 测试 **29/29**：`click_element`/`set_text` 在 WinForms 返回 `strategy:"message"`；WPF 按钮 Invoke、文本框 ValuePattern、复选框 Toggle、列表项 SelectionItem 均执行成功且前台恢复；WPF Label 返回 `ELEMENT_NOT_ACTIONABLE`。
- 构建 0 warning / 0 error；`dotnet format --verify-no-changes` 通过。
- 源码版本 `0.4.1-dev`，未打包；已发布仍是 `0.4.0-beta`。

**决策**
- 产品承诺从“默认不抢/用户活跃就拒绝”改为“执行优先，拒绝兜底”：先消息，再 UIA + 自动恢复；只有没有可执行 pattern、目标不可用或用户显式选择 strict 时才拒绝。
- 代价是 WPF/UWP 的 UIA 动作会短暂切换前台；`FocusGuard` 负责恢复并报告失败。这是当前的现实边界，不粉饰为“零打扰”。
- WGC 可见测试无法做到不闪窗，WPF UIA 测试无法做到零焦点切换，分别 opt-in；默认测试保持零可见窗口。
- 恢复测试接受屏外原位置的 OS clamp：`SetWindowPlacement` 会把完全屏外的普通窗口拉回工作区，这是系统行为，不是恢复失败。

**限制**
- WPF/UWP/自绘控件没有 HWND 子控件，UIA 动作会短暂激活目标；WPF 已验证可恢复，UWP 尚未实测；`FocusGuard` 恢复失败时只能报告 `FOCUS_STOLEN`，不能承诺 100% 不打断。
- 消息路径依赖目标处理 `WM_*`；Chromium/Electron 仍必须 CDP。
- UIA 动作的 UI 效果可能是异步的（WPF 按钮 click 事件在调用返回后才触发）；Agent 若立即 observe，可能需要短暂等待。

**下一步**
1. 真实 UWP 夹具验证 UIA 回退 + `FocusGuard`；评估非激活 pattern（Toggle/SelectionItem/ExpandCollapse 已覆盖）。
2. 24h soak + 4 target 混沌。
3. 多屏/混合 DPI、干净机器、签名/安装器。
